# Rails configuration audit

Audit date: 2026-09-03. Target: Rails 8.1 / Ruby 4.0.5.

The app was generated years ago and its `config/` had accumulated files and settings that
newer Rails versions either supply by default or no longer generate at all. This audit
compares every generated config file against the Rails 8.1 app generator templates
(`railties-8.1.3.1/lib/rails/generators/rails/app/templates/`) and removes what the
framework now owns.

Everything below is verified: `bin/rails runner` was used to confirm each removed setting
still resolves to the same value from framework defaults, and the full suite (763 examples)
passes before and after.

---

## Changed

### Framework defaults bumped to 8.1

`config/application.rb`: `config.load_defaults 8.0` → `8.1`, while the app already runs
Rails 8.1. The whole `new_framework_defaults_8_1.rb` set is now active:

| Setting | New value |
|---|---|
| `action_controller.escape_json_responses` | `false` |
| `active_support.escape_js_separators_in_json` | `false` |
| `active_record.raise_on_missing_required_finder_order_columns` | `true` |
| `action_controller.action_on_path_relative_redirect` | `:raise` |
| `action_view.render_tracker` | `:ruby` |
| `action_view.remove_hidden_field_autocomplete` | `true` |

The two behavioural ones were checked against the codebase: there is no
`redirect_to "relative/path"` anywhere (all redirects use path helpers or leading slashes),
and every model has a primary key, so `raise_on_missing_required_finder_order_columns` has
nothing to raise on. No `new_framework_defaults_8_1.rb` file is needed — the defaults were
adopted wholesale rather than one at a time.

### Deleted: `config/secrets.yml`

`Rails.application.secrets` was deprecated in 5.2 and **removed in Rails 7.2**; Rails no
longer reads this file at all. Nothing in `app/`, `lib/`, `config/`, `db/` or `spec/`
referenced it, and no deploy config (`app.json`, `Procfile`, `.github/workflows/`) mentions
it. It was dead weight that also kept two real dev/test `secret_key_base` values in git.

### Deleted: `config/initializers/cookies_serializer.rb`

Set `cookies_serializer = :json`, which is exactly what `load_defaults 7.0` and later
already set (`railties/lib/rails/application/configuration.rb:231`). Verified still `:json`
after removal. Rails stopped generating this file.

### Deleted: `config/initializers/session_store.rb`

Set `key: '_martigua2_session'`. Rails' `setup_default_session_store` initializer
(`railties/lib/rails/application/finisher.rb:52`) computes `"_#{app_name}_session"`, which
for `Martigua2::Application` is the identical `_martigua2_session`. Verified after removal.
Sessions are unaffected — same cookie name, same store.

### Deleted: `config/initializers/permissions_policy.rb`

100% commented out, and no longer part of the Rails 8.1 generator template set.
(`content_security_policy.rb` is also fully commented but *is* still generated by Rails 8.1,
so it was kept as the documented place to add a CSP.)

### Deleted: `config/initializers/redis.rb`

Opened a `$redis = Redis.new(...)` global connection at boot. `grep` across `app/`, `lib/`,
`config/` and `spec/` found zero references — the only hit was the assignment itself. Both
real Redis consumers configure themselves independently: `cache_store` via `REDIS_URL` in
each environment file, and Sidekiq in `config/initializers/sidekiq.rb`. This was a
connection opened on every boot for nothing.

### Deleted: `app/jobs/application_job.rb.keep`

A full `ApplicationJob < ActiveJob::Base` class saved under a `.keep` extension, so Zeitwerk
never loaded it — the class did not exist at runtime. It was neutered deliberately in
`20b02689 "remove application job"`; the `.keep` extension was just how the directory was
kept alive. Replaced with a plain empty `app/jobs/.keep`.

### `config/puma.rb`: removed the Solid Queue plugin

`plugin :solid_queue if ENV['SOLID_QUEUE_IN_PUMA']` shipped in the Rails 8 Puma template.
This app runs Sidekiq (`config.active_job.queue_adapter = :sidekiq`, a `worker:` line in
`Procfile`) and `solid_queue` is not in the Gemfile — setting that env var would have
crashed Puma on boot.

### `config/environments/production.rb`

- Removed a duplicated `config.active_support.report_deprecations = false` (the file set it
  twice, along with a repeated block of commented template hints).
- Added `config.active_record.attributes_for_inspect = [:id]`, the Rails 7.2+ production
  default. This app stores member names, emails and phone numbers; without it, a stray
  `inspect` on a record in a log line or an exception report dumps every attribute.

### `config/environments/development.rb`

Adopted three log-quality defaults that Rails 8.1 now generates and this file predates:

- `config.active_record.query_log_tags_enabled = true` — annotates SQL with the controller
  and action that issued it.
- `config.action_dispatch.verbose_redirect_logs = true` — logs the source line of a redirect.
- `config.action_view.annotate_rendered_view_with_filenames = true` — uncommented; the 8.1
  template ships it enabled. Development only, so system specs (test env) are unaffected.

### Header casing harmonised

`public_file_server.headers` used `'Cache-Control'` in development and test but
`'cache-control'` in production. Rails 8.1 templates use lowercase everywhere; all three now
match. HTTP header names are case-insensitive, so this is cosmetic.

### `config/routes.rb`: added the `/up` health check

`production.rb` already set `config.silence_healthcheck_path = '/up'`, but no such route
existed — the setting was silencing a 404. Added the conventional
`get 'up' => 'rails/health#show', as: :rails_health_check`.

## Deliberately not changed

### `config.assets.css_compressor = nil` — kept, comment corrected

This looked like a leftover: it carried a `# TODO: remove when get rid of scss` comment and
there is not a single `.scss` file left in `app/`, `lib/` or `vendor/`. Removing it broke
107 specs.

The reason is that `sassc-rails` is still a direct dependency (Administrate's engine ships
scss), and its railtie defaults `assets.css_compressor` to `:sass` in **every environment
except development** — which is why a `bin/rails runner` check in development reported `nil`
and looked like confirmation. In test and production, Sprockets then pipes Tailwind 4's
output through libsass, which cannot parse modern CSS and dies on
`rgb(from red r g b)`. The setting is load-bearing. It is now kept with a comment that says
why, instead of a TODO that invites the next person to make the same mistake.

### `config/initializers/wrap_parameters.rb` — kept

Rails 8.1 no longer generates this file, and the framework default is
`_wrapper_options.format == []`, i.e. params wrapping **off**. Deleting it would therefore
not be a no-op: it would stop wrapping JSON request bodies, and the app has JSON endpoints
(`messages`, `matches`, `sections`, `channels`, `webpush_subscriptions`). That is a
behaviour change, not configuration hygiene, so it needs its own change with request specs.

### `config.active_record.default_timezone = :local` — kept

Legacy (`:utc` is the Rails default), but flipping it reinterprets every timestamp already
in the database. That is a data migration, not a config change.

### Sprockets → Propshaft — not attempted

Propshaft is the Rails 8 default asset pipeline and this app still runs `sprockets-rails`
with an `app/assets/config/manifest.js`. The migration is real work with real risk: it
touches the Administrate engine's assets and the `sassc-rails` dependency above, and its
failure mode is visual, so it cannot be signed off by the test suite alone. It is worth
doing, but as its own change.

### `config/database.yml` production block

The `production:` block sets only `url:` and does not inherit `<<: *default`, so
`pool: RAILS_MAX_THREADS` is not applied there — the pool size comes from the
`DATABASE_URL` query string or Rails' default of 5. Worth confirming against the actual
`DATABASE_URL` and Puma's `RAILS_MAX_THREADS`, but merging `default` in blindly would also
drag in the local host/username/password keys, so it was left alone.
